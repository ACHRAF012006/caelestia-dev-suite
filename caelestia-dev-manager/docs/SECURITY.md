# Security and data ownership

Pasted/generated code is untrusted. Parsing, importing, manifest validation and Python AST validation do not execute component source. No component installer script, setup.py, postinstall hook, arbitrary manifest command or sudo operation is run. Installing copies inert files and writes manager-generated launchers/desktop entries/units. Launch/Enable is the reviewed transition to actual execution. Python dependency preparation is a separate explicit network action and uses binary wheels only; dependencies themselves still require trust.

Static checks do not make applications safe. Permissions metadata is a disclosure list, not a sandbox. Components execute with the user's permissions unless their own runtime provides stronger isolation. Services receive NoNewPrivileges but are not generally confined. Inspect code, dependencies and runtime behavior before activation.

IDs, manifest fields, service policies, desktop keys and relative source paths are constrained. Absolute paths, parent traversal, symlink ancestors, duplicate paths, file/directory conflicts and unsafe injected metadata are rejected. Installers choose fixed specific child destinations; source cannot direct writes to `/`, home roots, broad `.config`/`.local` parents, `/usr` or `/etc`. Parent directories may be created to hold approved children but are never recursively removed.

SQLite owns each exact installed file path once. Unowned existing files and paths owned by another component are collision errors. Receipts track checksum/mode; a modified installed file blocks update/uninstall. Take a backup, review edits, and resolve the modification rather than silently destroying it. Missing installed files are displayed and can be repaired with Update. Extra unowned files survive uninstall. Payload-directory cleanup uses empty-directory `rmdir` only. Directory trees are recursively removed only for explicit source deletion or private manager-created staging environments.

Desktop shortcuts have the same exact ownership, checksum and mode protections. XDG desktop configuration is parsed as inert data, allowing only HOME expansion and refusing command substitution, other variables, traversal, symlinks and broad/system targets. A reviewed path descriptor grants access only to one shortcut file, never to the entire desktop directory. Unrelated filename collisions require an explicit alternate selection; no existing file is silently replaced. Removing a shortcut never removes its parent directory or infers ownership from its name. Installed receipts preserve the original path when XDG configuration changes. Tests create shortcuts only under temporary roots, never on the real desktop.

Delete Source requires the exact component ID and warns when an installed copy remains. Uninstall stops applicable runtimes and removes owned installed files while leaving source. Disable preserves both. Plugin disable is a discovery change pending shell reload, not an immediate unload call.

Every installed file mutation creates a checksummed backup and a durable recovery journal before writing. Errors roll back touched files and registry receipts; a crash may require explicit recovery. Backups retain original paths and prior state and are checked before restore. This protects against ordinary failures, not a malicious process running as the same user, hardware failure, or complete loss of XDG state. No claim of filesystem-wide atomicity or transactional systemd state is made.

The upstream reference is ignored by Git and used only for inspection. The update helper checks origin/main, refuses local changes and uses fast-forward-only updates. Custom source is never written there. Logs/caches/backups/build output/secrets/staging are ignored. Automated destructive tests always use temporary paths; live checks use only unique harmless test IDs and never modify Caelestia runtime files.
